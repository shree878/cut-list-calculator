PLAN  -  Cut List Calculator
Version 1. Edit this file BEFORE changing scope. No code in this file.

======================================================================
1. SUMMARY
======================================================================
What: A free, no-login, browser-only website with separate tool pages that tell
trades people and DIYers how much material to buy and show a drawn cutting
layout. Calculations run in the browser. Nothing is uploaded.

Brand / site name: Cut List Calculator   (GitHub repo name: cut-list-calculator)
Reason: it is the plain phrase people type into Google. Names to avoid because
they already exist as products: CutPlan, CutList Optimizer, OptiCutter,
CutOptim, CutForgePro, TonCut, "Cut Calculator" (iOS app).
Note: the name was checked only with a few web searches. Before launch, check the
GitHub user/repo URL is free and do a quick trademark search.

Users: adults aged about 30 to 60 (carpenters, builders, tailors, DIYers), mostly
English-speaking, on phones, often outdoors or in bright workshops.
Language: English only at launch. All strings in a translation file so another
language can be added later (Spanish is the first candidate, decide after data).
Units: metric and imperial. Default chosen from browser locale, visible toggle.

Goals
 G1 Fast, trustworthy answer: how much to buy and exactly how to cut it.
 G2 Tool first, short pages, easy switching between tools.
 G3 Very readable: big text, strong contrast, dark mode, big tap targets.
 G4 Works offline after first visit.
 G5 Professional look, consistent on every page (DESIGN.md).
 G6 Free hosting on GitHub Pages.

Non-goals (for now)
 - No accounts, no server, no database, no ads, no paid features.
 - No CNC/DXF export, no 3D, no inventory management.
 - No promise of "zero waste". Results are an efficient layout, not guaranteed optimal.
 - No languages other than English, no blog until a later phase.

Market note: this space is crowded (web tools, iOS and Android apps, free and
paid). Our edge is not "nobody does this". Our edge is: free with no daily limits,
no login, readable by older eyes, phone-first, offline, honest about limits,
guillotine-aware layouts, printable cut lists. Re-check competitors before Phase 2.

2. LOCKED DECISIONS
======================================================================
 D1 Stack: Astro (static output), TypeScript strict, plain CSS with tokens,
    Vitest for tests, GitHub Actions deploy to GitHub Pages.
 D2 One real HTML page per tool and per search intent. No single-page app.
 D3 Pages are TOOL FIRST and SHORT. Long text lives in /help/, /about/, /guides/.
 D4 "i  How to use" button next to the tool title jumps to #how-to on the same page.
 D5 Footer carries small details: About ("Learn more"), Help, Guides, Privacy,
    "Calculations run in your browser".
 D6 Dark mode: follows device, header toggle, remembered, no flash.
 D7 Readability standard: body 18 px, inputs 20 px, nothing under 14 px,
    text contrast 7:1 or better in both themes, tap targets 48 px or larger.
 D8 Header tool switcher lists only tools that are LIVE.
 D9 Fonts: system font stack (nothing to download, works offline).
 D10 Home page "/" is the flagship tool (Linear cutting). It is not a landing page.
 D11 Phase order: 1 Linear (1D), 2 Plywood/sheet (2D), 3 Tiles, 4 Fabric.
     Why: 1D is small and proves the whole pipeline; sheet goods is the biggest
     audience and reuses 1D parts; tiles are simple maths; fabric has the most
     special rules (nap, pattern) and a different audience.
 D12 Output = print stylesheet (browser Print / Save as PDF) and a copy-link
    share URL. No PDF library (keeps pages light).
 D13 Heavy audits (Lighthouse) run in GitHub Actions, not on the dev laptop.

  2 Inputs (stock, pieces, basic settings; advanced settings collapsed)
  3 Calculate button
  4 Results summary (stock used, waste %, unplaced)
  5 Diagram
  6 Cut list (numbered cuts)
  7 Actions: Print, Copy link
  8 "Verify before cutting" note beside the results
 Below the tool (about 3 screens at most):
  9 #how-to: numbered steps (150 to 250 words)
 10 Assumptions and limits (about 100 words) + up to 5 real FAQs
 11 Related tools, then footer
 States every page must handle: empty (with "Try sample"), calculating,
 success, partial (some pieces unplaced), error (plain words, says how to fix),
 offline.

   OPUS   max 3 sessions from now on.

 EVERYTHING ELSE = HYDROGEN, including the offline mode (P1-T17), the share link, the audits,

 Effort: low = config, copy, deploy notes. med = default. high = UI state and tests that copy a
 pattern. xhigh = logic, audits, offline mode, anything that is hard to see is wrong.
 Why this is safe: every Hydrogen task is guarded by (1) automated tests, (2) the grep rules
 check in AGENTS.md, (3) the owner's visual check in the browser, and (4) free review: the owner
 uploads key files to the planning chat before the next task.
 Mandatory review points (upload the files): after P1-T09, P1-T14, P1-T15, P1-T17, P2-T04,
 and after each Hydrogen-built calculator logic module.

 Rules for Hydrogen tasks that write tests: expected values must be worked out by hand with the
 arithmetic in a comment. Never copy an expected value from the code's own output.
 Hydrogen tasks that copy a pattern must name the file they copied from in progress.txt.

 Order and switches: Phase 1: HYDROGEN T09 -> SONNET T10, T11 -> HYDROGEN T12..T21 -> OWNER T22.
 Phase 2: OPUS (T01+T02, then T03) -> HYDROGEN T04..T08. Phases 3 and 4 follow the model plan under each phase.

 Protocol: the owner states the active model (and HYDROGEN effort) in the first message of a session
 (see AGENTS.md). Before starting a task, the agent compares it with the task tag.
 If they differ, the agent does not start the task: it writes NEXT MODEL in progress.txt,
 commits, and tells the owner "Switch to <model>, then send the start prompt."
 A stronger model does a lighter task only when the owner says so. A weaker model never does a heavier one.
 Escalation: HYDROGEN stops and asks for help (a reserve Sonnet session) if it needs changes in
 src/algorithms/ or tests/algorithms/ beyond its own task, if npm test or npm run build still
 fails after 2 fix attempts, or if it is unsure. SONNET stops and asks for OPUS only for new
 algorithm design.
 Trial: P1-T09 is the first HYDROGEN task and P1-T17 the first xhigh logic-like task. The owner
 reviews them closely. If Hydrogen breaks the rules in AGENTS.md twice, spend a reserve Sonnet
 session on the failing task and tighten the prompt.

TASK NOTES (read the note for your current task before starting it)
======================================================================
P1-T08 note: keep the text the user typed and convert from that when the units toggle changes; never convert the displayed value repeatedly (rounding drifts).
P1-T10 note: validate.ts returns hard-coded English with internal units. Change it to return a stable error code (for example PIECE_TOO_LONG, KERF_NEGATIVE) plus the offending row and values. The UI builds the text from en.json using unit-formatted values via units.ts, never internal units.
P1-T18 note: delete public/404.html and use src/pages/404.astro instead.
P1-T04 note (API): solveLinear1D currently takes ONE stock length and buildResult uses that single length. Extend it to a stock list [{length, quantity}] (Infinity = unlimited) and let every open bar carry its own stockLength. When a new bar is needed, open the SHORTEST available stock that holds the piece. Reusable offcuts are extra stock entries with limited quantity. Keep a thin single-stock wrapper so the existing P1-T03 tests pass unchanged. Never use more bars of a length than its quantity; pieces that then do not fit go to unplaced.
P1-T04 note (choosing the better result): with one stock length, FFD and BFD that use the same number of bars always have the same total waste, so the "less waste" tie-break never fires. Between equal-bar results prefer the layout with the largest single leftover piece (more reusable); keep BFD as the final tie-break.
P1-T04 note (validation): validate.ts and linear1d.ts must use the same fit rule. With kerfAfterLast=false a piece equal to the stock length fits; with kerfAfterLast=true it does not. Check validate.ts agrees, or make both call one shared function.
P1-T06 note: fuzz tests must run the REAL solver (solveLinear1DMultiStock) on seeded random jobs, pass each result through toDisplayResult, and check: no overlap, placed + unplaced = requested by quantity, per-bar length conserved, never more bars of a stock length than its quantity, and never worse than one piece per bar. Edge cases: empty pieces, one piece, kerf larger than every piece, quantity 500, duplicate stock entries. Only new dependency: @vitest/coverage-v8 (note it in progress.txt). Target 90% line coverage on src/algorithms. If a fuzz test finds a real solver bug, fix it and say so clearly.
