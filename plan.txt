======================================================================
1. SUMMARY
======================================================================
What: A free, no-login, browser-only website with separate tool pages that tell
trades people and DIYers how much material to buy and show a drawn cutting
layout. Calculations run in the browser. Nothing is uploaded.

Brand / site name: Cut List Calculator   (GitHub repo name: cut-list-calculator)
Reason: it is the plain phrase people type into Google. Names to avoid because
they already exist as products: CutPlan, CutList Optimizer, OptiCutter,
CutOptim, CutForgePro, TonCut, "Cut Calculator" (iOS app).
Note: the name was checked only with a few web searches. Before launch, check the
GitHub user/repo URL is free and do a quick trademark search.

Users: adults aged about 30 to 60 (carpenters, builders, tailors, DIYers), mostly
English-speaking, on phones, often outdoors or in bright workshops.
Language: English only at launch. All strings in a translation file so another
language can be added later (Spanish is the first candidate, decide after data).
Units: metric and imperial. Default chosen from browser locale, visible toggle.

Goals
 G1 Fast, trustworthy answer: how much to buy and exactly how to cut it.
 G2 Tool first, short pages, easy switching between tools.
 G3 Very readable: big text, strong contrast, dark mode, big tap targets.
 G4 Works offline after first visit.
 G5 Professional look, consistent on every page (DESIGN.md).
 G6 Free hosting on GitHub Pages.

Non-goals (for now)
 - No accounts, no server, no database, no ads, no paid features.
 - No CNC/DXF export, no 3D, no inventory management.
 - No promise of "zero waste". Results are an efficient layout, not guaranteed optimal.
 - No languages other than English, no blog until a later phase.

Market note: this space is crowded (web tools, iOS and Android apps, free and
paid). Our edge is not "nobody does this". Our edge is: free with no daily limits,
no login, readable by older eyes, phone-first, offline, honest about limits,
guillotine-aware layouts, printable cut lists. Re-check competitors before Phase 2.

======================================================================
2. LOCKED DECISIONS
======================================================================
 D1 Stack: Astro (static output), TypeScript strict, plain CSS with tokens,
    Vitest for tests, GitHub Actions deploy to GitHub Pages.
 D2 One real HTML page per tool and per search intent. No single-page app.
 D3 Pages are TOOL FIRST and SHORT. Long text lives in /help/, /about/, /guides/.
 D4 "i  How to use" button next to the tool title jumps to #how-to on the same page.
 D5 Footer carries small details: About ("Learn more"), Help, Guides, Privacy,
    "Calculations run in your browser".
 D6 Dark mode: follows device, header toggle, remembered, no flash.
 D7 Readability standard: body 18 px, inputs 20 px, nothing under 14 px,
    text contrast 7:1 or better in both themes, tap targets 48 px or larger.
 D8 Header tool switcher lists only tools that are LIVE.
 D9 Fonts: system font stack (nothing to download, works offline).
 D10 Home page "/" is the flagship tool (Linear cutting). It is not a landing page.
 D11 Phase order: 1 Linear (1D), 2 Plywood/sheet (2D), 3 Tiles, 4 Fabric.
     Why: 1D is small and proves the whole pipeline; sheet goods is the biggest
     audience and reuses 1D parts; tiles are simple maths; fabric has the most
     special rules (nap, pattern) and a different audience.
 D12 Output = print stylesheet (browser Print / Save as PDF) and a copy-link
    share URL. No PDF library (keeps pages light).
 D13 Heavy audits (Lighthouse) run in GitHub Actions, not on the dev laptop.

3. TOOL PAGE TEMPLATE (identical on every tool)
======================================================================
 Above the fold on a 360 x 640 phone: the tool starts.
  1 Title + one-line promise + "i How to use" button
  2 Inputs (stock, pieces, basic settings; advanced settings collapsed)
  3 Calculate button
  4 Results summary (stock used, waste %, unplaced)
  5 Diagram
  6 Cut list (numbered cuts)
  7 Actions: Print, Copy link
  8 "Verify before cutting" note beside the results
 Below the tool (about 3 screens at most):
  9 #how-to: numbered steps (150 to 250 words)
 10 Assumptions and limits (about 100 words) + up to 5 real FAQs
 11 Related tools, then footer
 States every page must handle: empty (with "Try sample"), calculating,
 success, partial (some pieces unplaced), error (plain words, says how to fix),
 offline.

PHASE 1  LINEAR CUTTING (pipes, bars, lumber)   <- MVP
----------------------------------------------------------------------
Layer: core logic (pure modules, no DOM)
P1-T01 [OPUS] | Units module: parse decimals and inch fractions (e.g. 3 1/2), convert
        metric/imperial, integer internal units (0.1 mm / 1/64 in), format output.
        Accept: round-trip tests pass; bad input returns a clear error.
P1-T02 [OPUS] | Input validation: sizes > 0, kerf >= 0, piece longer than every stock
        reported as "cannot fit", quantity limits.
        Accept: every invalid case has a test and a plain-language message.
P1-T03 [OPUS] | 1D algorithm: First Fit Decreasing and Best Fit Decreasing, keep the
        better, kerf rule (clearly defined, optional kerf after last piece),
        deterministic.
        Accept: known-answer tests pass (see algorithm-testing skill).
P1-T04 [OPUS] | Multiple stock lengths, limited stock quantities, reusable offcuts as extra stock.
        Accept: tests for each; results never exceed available stock.
P1-T05 [OPUS] | Results model: per-bar pieces in cut order, waste, totals, waste %,
        unplaced list, plain-text cut list output.
        Accept: invariant tests (no overlap, all pieces accounted, length conserved).
P1-T06 [OPUS] | Test hardening: seeded fuzz tests, edge cases, 90% line coverage.
        Accept: coverage target met; npm test green.

Layer: UI
P1-T07 [SONNET] | Tool page template (ToolLayout) with title block, "i How to use" button
        and anchor target #how-to, below-tool sections in the fixed order.
        Accept: tool starts inside the first screen at 360 x 640.
P1-T08 [SONNET] | Stock + settings inputs: units toggle, stock length(s), kerf, advanced
        collapsed. Labels, units, hints, error text per DESIGN.md.
        Accept: keyboard-only use works; numeric keypad appears on phones.
P1-T09 [SONNET] | Pieces row editor: length, quantity, add, duplicate, delete; keeps data
        when editing; "Try sample" button.
        Accept: works with 50+ rows without slowdown; empty state is helpful.
P1-T10 [SONNET] | Calculate flow and results summary, partial and error states, polite
        screen-reader announcement.
        Accept: result appears in under 400 ms for typical jobs.
P1-T11 [SONNET] | SVG diagram: scaled bars, numbered pieces, sizes, waste hatch, cut order,
        title/description, scrolls inside its frame.
        Accept: readable in black and white; table equivalent exists (P1-T12).
P1-T12 [SONNET] | Cut list table (numbered cuts per bar) and "Verify before cutting" note.
        Accept: matches the diagram exactly; note visible beside results.

P1-T13 [SONNET] | Print stylesheet (diagram + cut list + summary, no chrome).

P1-T14 [SONNET] | Copy-link share URL that restores inputs; Copy as text.

======================================================================

 R2 Crowded market -> compete on readability, no limits, offline, honest limits.
 R3 Scope creep -> only the current phase is built; ideas go to the Parking Lot.
 R4 Slow SEO -> target long-tail pages first; expect months, not weeks.
 R5 Agent loses context -> AGENTS.md + progress.txt + commit per task.
 R6 Low-spec dev laptop -> few dependencies, heavy audits in CI.
 R7 Name or trademark clash -> check before launch (section 1 note).

11. MODEL SWITCHING (Antigravity cannot switch models by itself)
======================================================================
 Every task above carries a tag: [OPUS] for Opus 4.6, [SONNET] for Sonnet 4.6.
 OPUS = algorithm and logic work (P1-T01..T06, P2-T01..T04) and big plan changes.
 SONNET = everything else (setup, UI, styling, content, deploy, quality).
 Tasks are grouped so the model changes only a few times per phase:
   Phase 0 all Sonnet -> P1-T01..T06 Opus -> P1-T07 onward Sonnet -> P2-T01..T04 Opus -> rest Sonnet.
 Protocol: the owner states the active model in the first message of a session
 (see AGENTS.md). Before starting a task, the agent compares it with the task tag.
 If they differ, the agent does not start the task: it writes NEXT MODEL in
 progress.txt, commits, and tells the owner "Switch to <model>, then send the start prompt."
 If a [SONNET] task turns out to need hard algorithm design, the agent stops and
 asks the owner to switch to Opus instead of guessing.
